# Data model notes

- Entity primary and foreign keys are canonical, uppercase, 26-character ULIDs. Creation services generate them before database insertion; the database has no ID defaults. API validation rejects lowercase ULIDs instead of normalizing them, keeping database keys, signatures and audit records in one representation. Authentication secrets, invitation/reset tokens and sessions are separate cryptographically random values and are never ULIDs.

- `organizations` are the tenant isolation boundary and contain branding.
- `facilities` are optional branches inside an organization, not separate installations.
- `organization_memberships` establish broad admin, medical and support boundaries. Strict clinician-profession restrictions are intentionally out of scope.
- `facility_memberships` support assignment/reporting today and future policy without enforcing facility restrictions in Phase 1.
- `organization_entitlements` are effective-dated user limits; `NULL` means unlimited.
- Patient external references and identifying/contact profiles are stored only as encrypted byte arrays. Exact duplicate lookup uses a required, organization-scoped keyed hash; it must be produced with a separately protected key and must never be an unsalted plain hash of a predictable hospital identifier.
- Questionnaire definitions are versioned snapshots. `scope_key` is `GLOBAL` for shared definitions or the owning organization ID for overrides. It gives global rows NULL-safe uniqueness and lets assessments reference exactly one definition without a second, disagreeing version field. The API derives the scope from the selected definition; it is not accepted as client authority.
- measurement provenance can only be generated by the automated workflow.
- scoring requests use idempotency keys; results retain the external version and rule checksum.
- audit metadata must contain identifiers and safe context, never secrets or full clinical payloads.

Composite organization foreign keys prevent clinical records, facilities and acting memberships from crossing tenant boundaries. Every repository read must still require explicit organization context, and service-layer policy must enforce dynamic authorization. Negative cross-tenant integration tests remain mandatory before production.

## Seat reservations

Only one pending invitation per normalized email and organization is allowed. Active memberships plus pending invitations consume the configured limit. Database constraint triggers serialize changes with a transaction-scoped advisory lock and reject changes above the active entitlement. Invitation acceptance must update the invitation away from `PENDING` and insert/activate the membership in the same transaction. Repository code must translate the database check violation into `USER_LIMIT_REACHED` and retry serialization/deadlock failures safely.

## Audit immutability

The migration blocks updates, deletes and truncation through a trigger and revokes those privileges from `PUBLIC`. PostgreSQL owners and superusers can alter or disable triggers, so production must use a non-owner runtime role with only `SELECT` and `INSERT` on `audit_events`; the migration owner is reserved for controlled deployment work. Database backups and restricted infrastructure access remain necessary.
